# 数据库迁移与版本升级注意事项

适用于已有 PPGo_Job 数据库升级到本仓库包含任务高级搜索、Agent 主机监控与邮件告警的自定义版本。两份迁移脚本以已有的 v2.8.0 相关表结构为前提，不是空库初始化脚本，也不是任意旧版本的完整升级脚本。

推荐顺序：**副本预演 → 准备发布包 → 进入维护窗口并停旧主控 → 最终备份 → 数据库增量迁移 → 更新主控和页面 → 逐台更新 Agent → 验收并恢复任务 → 按需启用告警**。

## 升级前确认

- **记录版本**：保留当前部署的提交号、二进制或镜像、`views`、`static` 和启动方式；目标发布包也记录提交号。源码目录可用 `git rev-parse HEAD` 查看版本，实际部署版本以发布记录为准。
- **确认目标数据库**：核对部署环境 `conf/app.conf` 中的 `db.host`、`db.port`、`db.name`、`db.prefix`、`db.timezone`。迁移连接必须指向同一个库，先执行 `SELECT DATABASE(), VERSION();` 确认库名和数据库版本。
- **核对基础结构**：任务表应包含 `server_ids`，日志表应包含 `server_id`，服务器表应包含 `connection_type`。字段缺失时先确认原部署版本及完整表结构，再制定对应升级方案，不要跳过脚本的前置检查。
- **保存配置与密钥**：备份主控配置、Agent 的 `config/conf.ini` 或 `-c` 指定的配置、SSH 私钥、服务定义、外部任务脚本及其权限。不要用仓库示例配置覆盖部署环境原值，也不要把备份或凭据提交到 Git。
- **安排维护窗口**：记录升级前的启用任务和下次执行时间，评估长任务、关键业务时段、日志表大小、数据库剩余空间及复制延迟。提前约定停机期间错过调度的补跑方式，避免重复执行已完成的业务。
- **先做副本预演**：使用与实际部署相同的数据库版本、表前缀和接近真实规模的数据，演练备份恢复、迁移、应用启动和回退。副本环境应隔离生产 Agent、SSH 目标和通知渠道；主控启动会初始化任务调度，不要把试运行实例连接到生产库。

## 数据库迁移注意事项

### 迁移脚本与顺序

以下表名以默认前缀 `pp_` 为例。

| 顺序 | 脚本 | 主要变更 |
|---|---|---|
| 1 | [20261109_task_search.sql](../migrations/20261109_task_search.sql) | `pp_task` 增加 `owner_id`、`idx_task_search_owner`、`idx_task_search_creator`；`pp_task_log` 增加 `idx_task_log_latest_server` |
| 2 | [20261110_server_monitor.sql](../migrations/20261110_server_monitor.sql) | `pp_task_server` 增加 `monitor_alert_disabled`；新增 `pp_server_monitor_sample`、`pp_server_monitor_config`、`pp_server_monitor_state`、`pp_server_monitor_event` 四张表 |

- 已执行过搜索迁移且结构核验一致的环境，可直接执行监控迁移；首次升级到当前自定义版本时按表中顺序执行。
- 两份脚本均为增量变更，带有存在性检查。它们不会自动修正已经存在但定义错误的同名字段、索引或表，因此“重复执行未报错”不等于结构完全正确。
- 搜索迁移不回填历史负责人，原任务的 `owner_id` 默认值为 `0`，表示未分配；不会清理原任务日志。
- 监控迁移新增的 `monitor_alert_disabled` 默认为 `0`，即单机告警开关开启；**首次启用监控时全局告警默认关闭**。已有监控配置会持久保存，再次部署不会自动重置开关。
- 当前程序启动流程不自动执行 `migrations/` 中的 SQL。即使暂时不用监控，升级程序前也要补齐新增字段和表。

**不要向已有业务库重新导入根目录的 `ppgo_job2.sql`。该文件含 `DROP TABLE IF EXISTS`，会删除已有表，而且旧初始化结构与当前模型存在差异。Docker 的初始化 SQL 同样不应当作增量升级脚本。**

### 备份与执行条件

1. 备份整个应用数据库的结构和数据，而非仅备份本次新增表。记录备份时间、数据库版本、文件位置和恢复步骤，并在隔离库完成恢复核验。存在自定义触发器、存储过程或事件时，一并纳入备份范围。
2. 使用 `mysqldump --single-transaction` 时，一致性保证针对 InnoDB 表；存在其他存储引擎的表时另行确认一致性备份方式。备份期间避免并发执行表结构变更，备份命令成功结束并核验后再迁移。见 [MySQL 备份选项说明](https://dev.mysql.com/doc/refman/8.0/en/mysqldump.html#option_mysqldump_single-transaction)。
3. 迁移账户须具备目标库所需的查询、建表、改表及建索引权限。迁移后仍使用原应用账户启动，并确认它具备新增监控表的读写、清理权限。
4. 大日志表建立索引可能等待锁、占用磁盘和增加复制延迟。先用副本测量耗时，为维护窗口和临时空间留出余量；不要把迁移与其他 DDL 同时执行。
5. MySQL 的 `ALTER TABLE`、`CREATE TABLE` 等 DDL 会隐式提交；给整个脚本套上 `BEGIN` 并不意味着失败后可以整体 `ROLLBACK`。中途失败时，先核对已完成的变更，再决定重试。见 [MySQL DDL 隐式提交说明](https://dev.mysql.com/doc/refman/8.0/en/implicit-commit.html)。

### 执行示例

下列命令用于 **Bash**，在目标版本的源码根目录运行。执行前完成备份，替换 `DB_HOST`、`DB_PORT`、`DB_MIGRATOR`、`DB_NAME`，并将示例中的 `pp_` 换成实际 `db.prefix`；密码通过提示输入。

```bash
set -euo pipefail

for migration in \
  migrations/20261109_task_search.sql \
  migrations/20261110_server_monitor.sql
do
  printf '执行迁移：%s\n' "$migration"
  {
    printf '%s\n' "SET @ppgo_prefix = 'pp_';"
    cat "$migration"
  } | mysql --protocol=TCP --host=DB_HOST --port=DB_PORT \
      --user=DB_MIGRATOR --password --database=DB_NAME \
      --default-character-set=utf8mb4 --batch
done
```

- 每个脚本都在自己的同一连接内先设置 `@ppgo_prefix`；在另一个客户端窗口设置该变量不会影响本次迁移。
- 不要添加 `mysql --force`，也不要在客户端配置中开启遇错继续；保留终端输出和退出状态，第一份脚本出错时停止后续发布。见 [MySQL 批处理错误处理说明](https://dev.mysql.com/doc/refman/8.0/en/batch-mode.html)。
- Windows 使用数据库客户端时，选择正确数据库，按顺序执行完整脚本，启用遇错停止，并把前缀设置与对应脚本放在同一连接内。上面的 Bash 命令不适用于直接粘贴到 PowerShell。

### 迁移后核验

在目标库执行以下只读检查；使用自定义前缀时替换表名中的 `pp_`。

```sql
SHOW COLUMNS FROM pp_task LIKE 'owner_id';
SHOW COLUMNS FROM pp_task_server LIKE 'monitor_alert_disabled';
SHOW INDEX FROM pp_task;
SHOW INDEX FROM pp_task_log;
SHOW CREATE TABLE pp_server_monitor_sample;
SHOW CREATE TABLE pp_server_monitor_config;
SHOW CREATE TABLE pp_server_monitor_state;
SHOW CREATE TABLE pp_server_monitor_event;
```

对照迁移脚本确认字段类型、默认值、索引列顺序及四张表的完整定义，特别是采样、告警状态和投递记录的唯一键。抽查原任务、执行日志、用户权限和服务器配置仍在；确认全部完成后再启动新版程序。

## 版本更新注意事项

### 准备发布包

使用 `go.mod` 要求的 Go 1.22 或更高版本，在与线上运行目录分离的源码根目录准备发布产物，保留仓库中的 `go.mod` 和 `go.sum`，不在本次发布中顺带升级依赖。以下是 Linux amd64 的 Bash 构建示例，其他架构应匹配目标主机：

```bash
set -euo pipefail
mkdir -p release
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o release/PPGo_Job .
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o release/ppgo_agent ./agent
```

- 主控二进制、`views`、`static` 必须来自同一提交，并同时发布；只替换二进制容易造成页面和接口不匹配。
- 根目录 `run.sh` 使用文件名 `PPGo_Job`，`agent/run.sh` 使用 `ppgo_agent`。采用自定义文件名时，同步检查服务启动命令、工作目录和执行权限。
- Agent 默认从工作目录下的 `config/conf.ini` 加载配置；使用 `-c` 时保留原路径。原 `ServerId`、主控地址和端口等设置应保持一致，避免产生错误节点关联。
- 现有 `package.sh` 的主控打包清单不包含 `migrations/`、升级文档或 Agent 二进制；使用该脚本发布时，单独附带对应迁移文件、文档和 Agent 产物。包内的旧初始化 SQL 不用于已有库升级。

### 发布顺序

1. **进入维护窗口**：限制管理页面和 API 的配置变更，按业务安排暂停新触发，记录原启用状态并等待在途任务结束。停止主控不代表远程命令已经结束，必要时在 SSH 目标及 Agent 上核对进程；不要依赖重启自动处理遗留任务。
2. **停止旧主控**：使用实际部署的服务管理方式停止，并防止守护进程自动拉起。确认旧进程已退出，再做最终备份和迁移；同一数据库只运行一套主控调度器，避免重复派发任务。
3. **完成数据库迁移**：按上文顺序执行和核验。任何报错先处理，再进入程序替换步骤。
4. **更新主控**：替换二进制及同版本 `views`、`static`，保留原配置、密钥和日志，按原运行账户及工作目录启动。检查启动日志、数据库连接、页面和权限；必要时刷新浏览器及代理静态资源缓存。
5. **逐台更新 Agent**：在对应节点空闲、无在途任务时先升级一台 Linux Agent，确认心跳和任务执行正常，再扩展到其他节点。主控升级后，旧 Agent 的任务 RPC 和心跳保持兼容，未升级节点显示不支持监控，不会自动停用。
6. **恢复业务与告警**：按记录仅恢复升级前应启用的任务，核对维护窗口漏跑及可能重复执行的业务。首次上线保持全局告警关闭，确认采样、磁盘目录、收件人和 SMTP 后再显式开启。

现有 `run.sh` 通过 `killall` 按进程名停止服务，同机有多个同名进程时会一起受到影响；使用能准确定位目标实例的服务管理方式，并以实际进程状态确认停机结果。

### 主机监控专项检查

- 本次主机资源采集面向 Linux Agent，不涵盖 SSH、Telnet 节点或主控本机执行。不要把未接入监控当作任务执行故障。
- Agent 可在原配置中添加 `MonitorDiskPath=/data`；未配置时默认采集 `/` 所在文件系统。数据写入独立挂载盘时，选取真实数据目录，并确认 Agent 运行账户有访问权限。
- 采样间隔为 60 秒，CPU 需要相邻两次成功采样后才有结果；升级或重启后短暂显示未知属于预期。等待采样后检查内存、磁盘路径及历史曲线。
- 升级沿用原 Agent 端口，将网络访问范围限制为主控。Agent 的现有 Windows 信号处理尚未支持 Windows，本次监控升级不代表新增 Windows Agent 支持。
- 全局告警由超级管理员配置。已有告警环境升级前记录开关、活动事件和收件人；关闭开关会结束相关状态并取消待发通知，因此不要把切换开关当成无副作用的暂停方式。具体规则见 [主机监控与资源邮件告警](server-monitor.md)。

### Docker 部署补充

- 当前 `.docker/web/Dockerfile` 复制根目录的 `PPGo_Job`、`conf/app.conf`、`views` 和 `static`，不在镜像内编译 Go。先准备匹配容器架构的 Linux 二进制及正确配置，再重新构建、替换 `web` 镜像；仅拉取源码或重启旧容器不等于更新程序。
- 迁移仍需单独连接现有数据库执行。保留 `db` 服务使用的数据挂载和实际数据库配置，不要为了升级应用重建一个空数据库。
- 仓库 Compose 示例把数据绑定到 `.docker/_local_mysql_data`。不要删除该目录或实际部署的数据卷；更换发布目录时核对绑定路径仍指向原数据，避免连接到新空库。不要把删除数据卷的命令作为发布步骤。
- 数据库大版本、基础镜像和应用功能升级分开安排，分别验证兼容性和回退方案。

## 失败处理与回退

| 场景 | 处理方式 |
|---|---|
| 迁移中途失败 | 停止后续发布，保留报错和当前表结构。确认目标库、权限、磁盘及锁等待，修复原因后核对已成功语句，再重跑对应增量脚本；不要直接删表重建 |
| 迁移成功但新版程序异常 | 停止新版，恢复升级前同一套主控二进制、页面和配置，再核对调度与权限。本次迁移为新增字段、索引和表，回退到升级前已验证版本时可保留这些结构 |
| 部分 Agent 升级异常 | 暂停这些节点的新任务，确认在途任务处理完毕后恢复原 Agent 二进制及配置，保留原节点身份；核对心跳、任务结果和监控告警状态 |
| 出现数据误删或其他损坏 | 停止相关写入，保存现场，先在隔离库验证备份及恢复点，再安排正式恢复。全库恢复会覆盖备份之后的任务配置、日志和其他新数据，需先确认损失范围及补偿方案 |

正常版本回退不需要删除 `owner_id`、监控字段或四张监控表，也不应清空已经维护的负责人、活动告警和投递记录。回退后再次升级仍要核验结构；本节保留结构的结论仅针对上述两份增量迁移，后续版本如有删除或数据转换，应另行评估。

## 上线验收清单

- [ ] 发布记录包含旧版与新版提交号、发布包、备份位置、迁移执行结果和实际停机时间。
- [ ] 新字段、三个搜索索引和四张监控表与脚本定义一致，原业务数据抽查正常。
- [ ] 只有预期的主控实例在调度；任务启停状态与升级前记录一致，遗漏或重复执行风险已处理。
- [ ] 管理员及普通用户的任务列表、审核、负责人、高级搜索、服务器分组权限正常。
- [ ] 在专用测试任务上验证当前使用的执行方式，结果能落库并被搜索命中；不直接拿真实业务任务试跑。
- [ ] 已升级 Agent 的心跳、任务执行和主机指标正常，旧 Agent 的任务执行保持正常。
- [ ] 页面使用新版静态资源，启动及运行日志没有缺表、缺列、数据库权限或持续采集错误。
- [ ] 需要告警的环境已确认收件人和 SMTP；不需要告警的环境保持关闭，并留存原配置记录。

自动化验证入口见 [任务高级搜索](task-search.md) 和 [主机监控与资源邮件告警](server-monitor.md)。数据库集成测试只使用专用隔离测试库；未配置 `PPGO_TEST_MYSQL_DSN` 导致的 `SKIP` 不视为迁移验证通过。
