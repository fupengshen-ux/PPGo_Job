# v2.8.0 自定义版：任务高级搜索

本次只增强任务管理层，保留 SSH、Agent 和现有调度策略，不包含服务器监控、告警或实时执行中筛选。

## 使用方式

普通任务列表与审核列表均支持任务 ID、名称包含匹配、负责人、创建人、分组、任务状态、执行服务器、创建日期和最近执行结果组合查询。条件之间采用 AND；查询、重置和个人快捷筛选回到第一页，翻页保留筛选条件。名称中的 `%`、`_` 按普通字符匹配。

“我负责的”和“我创建的”分别设置人员条件并清除另一人员条件，保留其他筛选项。负责人仅用于管理，角色和分组仍决定任务可见范围。人员选项包含停用用户，便于检索历史任务；新分配负责人只接受启用用户。历史任务负责人为“未分配”，新建任务默认创建人，复制时保留有效负责人。

普通任务页默认显示启用/停用任务；审核页默认显示待审核/审核未通过任务。启用表示参与调度，不表示此刻有进程正在执行。

### 最近执行结果的准确含义

1. 对任务**当前配置**中的各个服务器（包括本机 `0`），按日志 `create_time DESC, id DESC` 取最后一条已记录结果。`create_time` 是执行开始时间，而非写入时间或结束时间。
2. 汇总各节点的成功、失败、超时、无记录数量。已从任务配置移除的节点不参与汇总；重复节点 ID 只统计一次。
3. 指定服务器筛选时，只判断该节点的结果；未指定时统计所有当前配置节点。
4. “全部成功”要求至少有一个有效节点，所有节点有记录且均成功；“存在异常”包含失败或超时；失败、超时、部分无记录可同时命中。
5. “部分无记录”表示有的节点有日志、有的没有；“全部无记录”表示所有当前节点没有日志。无有效节点的任务显示“未配置执行节点”，不归类为成功或全部无记录。
6. 执行中沿用上一次结果；首次执行尚未产生日志时显示无记录。日志删除后以剩余日志重新计算，不将无记录等同于从未执行。
7. 汇总不代表同一轮调度。轮询任务各节点的最新记录可能来自不同时间。

## 接口兼容

继续使用 `/task/table`，保留 `code/msg/count/data` 响应以及旧字段。

| 参数 | 说明 |
|---|---|
| `page` / `limit` | 页码从 1 开始，默认 1/30，每页最多 100 |
| `task_id` / `task_name` | 正整数任务 ID、名称包含匹配；兼容旧审核页 `taskName` 别名 |
| `owner_id` / `create_id` | 空值为全部，0 分别表示未分配/未知创建人 |
| `group_id` | 0 为全部可见分组；指定 ID 仍与当前用户的分组权限取交集 |
| `status` | 旧参数：2 选择审核列表范围，其他值维持普通列表范围 |
| `task_status` | 可选精确状态 0/1/2/3，进一步收窄上述页面范围 |
| `server_id` | 空值全部，0 本机，正整数按完整服务器 ID 匹配 |
| `created_from` / `created_to` | `YYYY-MM-DD`，按 Asia/Shanghai 解释，结束日期包含当天 |
| `latest_result` | `all`、`success`、`any_error`、`failed`、`timeout`、`partial_missing`、`no_record` |

新增响应字段：`task_name_raw`、`owner_id`、`owner_name`、`create_id`、`create_name`、`create_time`、`latest_execution_summary`。汇总对象包含 `total_count`、`success_count`、`failed_count`、`timeout_count`、`no_record_count`、`latest_time`（统计范围内最新日志的开始时间戳，缺失为 0）。

任务保存接口和 `/task/apitask` 增加可选 `owner_id`：旧客户端省略时，新建默认有效创建人，更新保留原负责人；显式传 0 清空负责人。原 API 的认证方式和审核行为保持原样，应继续限制其网络访问范围。

## 构建、迁移与发布

仓库使用模块路径 `github.com/george518/PPGo_Job`，确保内部导入引用本地修改，而非重新下载上游 v2.8.0。`go.mod` / `go.sum` 固定依赖，保留 Beego 1.x；不包含大版本框架升级。使用 Go 1.22 或更高版本构建。

1. 备份生产数据库，先在数据库副本上验证。根目录旧初始化 SQL 与 v2.8.0 模型有差异，不要重新导入它覆盖生产库。
2. 核对实际任务表包含 `server_ids`、日志表包含 `server_id` 等 v2.8.0 字段。
3. 在目标数据库执行 `migrations/20261109_task_search.sql`。若表前缀不是 `pp_`，先在**同一连接**执行 `SET @ppgo_prefix='实际前缀';`。脚本含前置字段检查、重复执行保护；使用批处理时不要加 mysql 的 `--force`。
4. 脚本添加 `owner_id` 和三个索引，不回填历史负责人、不清理日志。大日志表创建索引可能持锁或消耗磁盘，安排维护窗口。
5. 执行 `go build -o ppgo-job-custom .`，打包二进制及更新后的 `views`、`static`，保留环境原有配置和密钥。
6. 按现有单实例部署流程停止旧调度器、替换并启动新版，避免新旧实例同时调度。核对用户权限、搜索结果以及任务启停。

回退时停止新版、恢复旧二进制和页面，保留新增字段/索引即可；不删除用户已维护的负责人数据。

## 开发验证

单元测试及控制器测试：

```sh
go test ./models ./controllers -run 'Test(TaskSearch|ParseTaskSearch)' -count=1 -v
node --test tests/task-search-ui.test.cjs
```

原 v2.8.0 的 `controllers/common.go` 存在 `AuthUrl != " " || AuthUrl != "/"` 的历史 vet 告警。本次保留该处既有逻辑；若默认测试因此中止，可对控制器功能测试单独使用 `go test -vet=off ./controllers -run 'Test(TaskSearch|ParseTaskSearch)' -count=1 -v`。这不表示全仓库 vet 检查通过。

真实数据库集成测试需要显式设置 `PPGO_TEST_MYSQL_DSN`，数据库必须是本机 TCP 地址且库名以 `_test` 结尾。例如 `TEST_USER:TEST_PASSWORD@tcp(127.0.0.1:33307)/ppgo_search_test?charset=utf8mb4`。测试使用唯一表前缀并清理自己创建的表，不读取生产配置；未设置环境变量时集成测试会显示 SKIP，而非通过。

覆盖迁移重复执行、名称特殊字符、组合权限、时间边界、多节点混合结果、并发落库顺序、删除日志、节点变化、分页、负责人保存/复制/旧 API，以及两万条日志下的最新结果索引选择。JavaScript 测试覆盖重置、分页回到第一页、快捷筛选、回车与结果文本转义。
